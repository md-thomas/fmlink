Phase 2: Link-Layer Framing - MOSTLY DONE
--------------------------------------------
Implemented in openwave_link.py, shared by phy_sim_loopback.grc, tx_pluto.grc,
and rx_rtlsdr.grc's epy_blocks so the flow graphs can't drift on framing.

  [x] 2.1 Preamble replaced: 32-byte LFSR pseudo-noise sequence (9-bit
          register, taps 1/2/5/9) instead of the old repeating 0x55 x8
          pattern - sharp autocorrelation peak (~9% worst sidelobe) vs. the
          old pattern's ~99% sidelobes, for reliable frame-start detection
          under noise. Sync word (0x1ACFFC1D) unchanged.
  [x] 2.2 Real 32-byte header (build_header/parse_header): Version, Packet
          Type, Waveform Mode ID, Flags, Sequence Number, Source ID,
          Destination ID, Payload Length, Reserved - matches
          OpenWave_Specification.txt's byte layout exactly (struct '>BBBBH8s8sH8s').
          Mode ID and Source/Destination ID are written at the correct
          offsets but are placeholder values on TX and not yet parsed/acted
          on by RX.
  [x] 2.3 CRC32 over Header+Payload (build_frame/FrameParser); RX now knows
          exact frame length from the header's Payload Length field instead
          of scanning for a zero-run marker, and drops frames on CRC mismatch.
  [x] 2.4 stream_display_sink's marker-scanning hack replaced by
          FrameParser's incremental, CRC-verified header/payload collection.
  [x] 2.5 ACK/retry: build_ack_frame() + RetryManager (max_retries/timeout,
          pure state machine, no RF knowledge) using the ACK Requested/ACK
          Response Flags bits and Sequence Number. Wired into a real closed
          loop in phy_sim_loopback.grc only (RX ack_needed -> ack_responder_0
          -> TX/channel -> RX -> ack_received); tx_pluto.grc/rx_rtlsdr.grc
          are structurally one-directional (RTL-SDR RX can't transmit, Pluto
          TX has no RX chain) so they can't close this loop yet - ready for a
          future full-duplex pairing.
  [x] 2.6 Fragmentation: build_fragmented_frames()/FragmentReassembler using
          the Fragmented/More Fragments Flags bits, each fragment sent as its
          own independent burst. Fragmented sends are NOT ACK/retry-tracked
          in this phase regardless of ack_requested.
  [x] 2.6b Fragment Index header field (1 of the 8 Reserved bytes
          repurposed, 7 remain reserved - see OpenWave_Specification.txt) so
          a receiver has an authoritative "is this really a new run" signal
          instead of inferring it from "nothing else in progress." Fixes a
          real bug found via large-message testing: a run abandoned mid-
          stream (e.g. MAX_FRAGMENTS overflow) used to let the next leftover
          continuation fragment be misread as a fresh start, silently
          delivering a truncated TAIL of the original message as if it were
          a complete, valid one (normal 'ok' status, no error indication).
          FragmentReassembler now also tracks expected Source ID per run, so
          two stations' fragmented messages with coincidentally-matching
          sequence numbers can't merge either.
  [ ] 2.7 Dynamic ACK timeout based on active Waveform Mode's bit rate
          (RetryManager.timeout_s is currently a fixed default, not derived
          from mode/symbol rate).
  [x] 2.11 Wire RetryManager/ACK into the GNU-Radio-free pipeline - done in
          ota_station.py (Phase 8): --ack requests an ACK and retries on
          RetryManager timeout, closing a real loop over the live OTA
          simulator link. This is stop-and-wait per single-fragment
          message, not a windowed/selective-repeat scheme, and (matching
          build_fragmented_frames()'s existing rule) does NOT track
          fragmented multi-frame sends - a windowed scheme for those is
          still a real follow-up if it turns out to matter in practice.
          openwave_cli.py/file_xfer_test.sh themselves remain unwired
          (still one-shot, no live RX to ACK against).
  [x] 2.8 Parse/act on Waveform Mode ID and Destination ID on RX, in
          rx_rtlsdr.grc only: openwave_link.format_mode()/decode_station_id()
          decode and display both; a new station_id parameter (blank by
          default = unfiltered, matching every current TX chain's all-zero
          placeholder Destination ID) enables address filtering via
          openwave_link.is_for_station() - non-matching frames are dropped
          and counted under 'not_for_us'. phy_sim_loopback.grc's loopback RX
          does not have this (out of scope - self-loopback, no real
          addressing to test).
  [ ] 2.9 Consider closing the ACK loop for tx_pluto.grc/rx_rtlsdr.grc once
          a full-duplex hardware pairing exists (needs a second radio pair
          or TDD scheme, not just software).
  [x] 2.10 LinkReceiver class + iter_frames()/describe_frames() added to
          openwave_link.py: the RX dispatch logic (address filtering, ACK/
          fragment handling, seq gap/dup tracking, stats) as a plain Python
          class, driven by byte-level frame scanning rather than a GNU Radio
          bitstream. This makes the *entire* link layer (not just framing)
          usable/testable with zero GNU Radio dependency - see the "no GNU
          Radio" note under Phase 5. rx_rtlsdr.grc's epy_block still has its
          own separate copy of the same dispatch logic (predates this) -
          not yet refactored to share LinkReceiver, a follow-up worth doing
          to remove the duplication.

Phase 3: Forward Error Correction & Interleaving - MOSTLY DONE (CLI pipeline)
-----------------------------------------------------------------
Implemented in openwave_fec.py: convolutional encoding + hard-decision
Viterbi decoding (numpy-vectorized), fully parameterized by generator
polynomials/constraint length K rather than hardcoded to one scheme.
Wired into the GNU-Radio-free CLI pipeline (fec_encode.py/fec_decode.py,
pipeline_test.sh/file_xfer_test.sh), which is the sole actively developed
PHY path. The archived GNU Radio chain (legacy/gnuradio/) was never wired
up and still runs uncoded, but is no longer part of the active plan.

  [x] 3.1 FEC scheme picked and integrated (for the CLI pipeline): rate
          1/N convolutional coding, PRESETS table of 13 named
          configurations (r1_2_k3 through r1_6_k9), free_distance()/
          find_generators() for principled (Dijkstra-based) preset
          selection instead of hand-picked polynomials. Each fragment of a
          multi-fragment message is FEC-protected independently.
          openwave_fec_generate_presets.py regenerates/extends the table.
          LDPC was considered (see this session's discussion) but not
          pursued - would need a new codec built from scratch (parity-
          check matrix design, encoder, iterative belief-propagation
          decoder) for a coding-gain benefit, not a speed one; convolutional
          + vectorized Viterbi already meets current needs.
  [ ] 3.2 Bit interleaver/de-interleaver to break up burst errors - not
          built. Current FEC handles scattered bit errors within a
          fragment; a burst that takes out a large contiguous run within
          one fragment's coded block is a different failure mode this
          doesn't address (a lost/undecodable fragment's marker - see
          openwave_sync.py's 'gap' status - is the closest analogue
          currently handled, but that's sync-level, not interleaving).
  [x] 3.3 Re-ran (via file_xfer_test.sh, not phy_sim_loopback.grc's BER
          test specifically) FEC-vs-uncoded comparisons across SNR/preset
          combinations - see openwave_fec.py's empirically-measured
          SNR-to-preset table (right after PRESETS) for concrete pass-rate
          numbers, e.g. r1_2_k3 fully reliable at 3dB, r1_4_k9 needed at
          -6dB where r1_4_k7 only holds ~86%. Phase 1's archived GNU Radio
          loopback graph itself was never re-run with FEC enabled (FEC
          isn't wired into it - see above; no longer applicable now that
          Phase 1 is archived).

Phase 5: Audio-Interfaced Radio Deployment (Eventual Target) - NOT STARTED
------------------------------------------------------------------------------
The actual deployment target: driving real transceivers (VHF/UHF radios)
through their audio ports instead of SDR hardware. Distinct from the
archived SDR work in Phase 4 - this is about the I/O interface (soundcard
in/out + PTT), not any one modulation - the modem is now pluggable
(BPSK/QPSK/16-QAM today, see openwave_link.py's WAVEFORM_MODES), not
pi/4-QPSK-specific.

No GNU Radio, eventually: this direction has effectively started - the
pure-Python CLI pipeline (openwave_modem.py/openwave_pulse.py/etc.) already
is the GNU-Radio-free path anticipated here, and is now the sole actively
developed PHY (Phase 4's GNU Radio chain is archived, not a parallel
track). Real-time audio I/O and PTT (5.1/5.2 below) are now done too (2026-10-04),
so this is a GNU-Radio-free path all the way to real radios.
Favor keeping core logic (openwave_link.py already has zero GNU Radio
imports, including the LinkReceiver dispatch class - see 2.10) portable.

  [x] 5.1 Real-time audio I/O (2026-10-04, openwave_radio.py): stream the pluggable-PHY baseband (see

  [x] 5.4 Over-the-air test (2026-10-04, see RADIO_SETUP.md) between two audio-interfaced radios running

          DONE 2026-10-04 on the mic port: an HT on an AIOC and an HT on a

          mode 2 r1_2_k3 near 7 dB (see RADIO_SETUP.md's own table). Used
          to calibrate select_mode_for_snr()'s probe-rate penalty
          (10*log10(rate/600)).
          FLAGGED 2026-10-06, not yet root-caused: a fresh run of
          audio_margin_sweep.py on another machine, with the exact same
          default arguments, reproduces mode 0's row closely (-1 to -2 dB)
          but puts mode 1's 50%-delivered point near ~1.75 dB and mode 2's
          near ~5.0 dB - 2.5-3 dB more pessimistic, in both a 24-trial and
          a 100-trial/finer-sigma-step run (so not just averaging out with
          more trials). Cross-checked against gr-open_modem (a GNU Radio

          of build_samples/decode_samples, fed the identical burst and the

          the cause. Candidates, unconfirmed: a numpy version difference
          changing default_rng(7)'s output sequence, or environment drift

          version at measurement time vs now, before trusting this table's
          exact dB values for new link-margin work - the relative ordering
          (mode 0 most noise-tolerant, then 1, then 2) still held in both
          runs.

Phase 6: Multi-Modulation Support - IN PROGRESS (CLI pipeline)
-----------------------------------------------
Long-term goal: make Waveform Mode ID select among multiple modulations
(BPSK, QPSK, 8PSK, 16QAM, OFDM). Started 2026-08-19 in the GNU-Radio-free
CLI pipeline (openwave_modem.py/modulate.py/demodulate.py), which now
implements BPSK, QPSK, and 16-QAM. This is now the project's sole actively
developed PHY - Phase 1's pi/4-QPSK GNU Radio chain has been archived
(legacy/gnuradio/), not kept in parallel; pi/4-QPSK's differential ring
variant is no longer a planned addition here.

  [x] 6.1 Modulator/demodulator selection is pluggable via a dict lookup
          (MODULATORS/DEMODULATORS in modulate.py/demodulate.py, keyed by
          the -t flag) rather than hardcoded - not yet driven by Waveform
          Mode ID specifically (that's the negotiation piece, 6.4).
  [x] 6.2 QPSK and 16-QAM added: openwave_modem.py's QPSK_POINTS/QAM16_POINTS
          + modulate/demodulate pairs - both Gray-coded (I and Q are
          independent axes - 1 bit/axis for QPSK, 2 bits/axis as 4-level
          PAM for 16-QAM - each with its own hard decision on demodulate,
          so a small perturbation only ever flips one bit at a time), unit
          average symbol energy (same convention as BPSK_POINTS) so
          channel.py's SNR-vs-signal-power measurement treats all three
          schemes comparably. Verified end to end through
          pipeline_test.sh/file_xfer_test.sh's --modtype flag: each step
          up costs ~3dB of SNR margin for the same link reliability (e.g.
          with r1_3_k7: BPSK holds to ~-6dB, QPSK to ~0dB/-3dB, 16-QAM
          needed 3dB where QPSK already worked at 0dB) - the expected,
          correct real-world Eb/N0 tradeoff for packing more bits into the
          same symbol energy, not a bug. 8PSK is the remaining natural
          extension of this same constellation-dict approach. pi/4-QPSK's
          differential ring variant (Phase 1, archived) is not currently
          planned as an addition here.
  [ ] 6.3 Design an OFDM mode (bigger lift - new sync/framing needs, not a
          drop-in replacement for the single-carrier chain).
  [ ] 6.4 Define mode-selection/negotiation behavior at the link layer.
          Concrete direction discussed this session, inspired by HF ALE
          (Automatic Link Establishment): RX estimates SNR and reports
          back a recommended mode/rate/FEC preset via a control message
          (PACKET_TYPE_CONTROL already exists in the header for this);
          TX then switches for subsequent payload frames. Needs (a) an
          FEC-preset field in the header (currently --fec is CLI-only, not
          signaled in-band) and (b) a bootstrapping rule - negotiation/
          control frames themselves must always use the most robust fixed
          scheme, since TX can't know a good scheme for a link it hasn't
          heard back about yet. Depends on 2.11 (ACK/control feedback
          channel in the CLI pipeline) for the RX-to-TX report path.
  [ ] 6.5 openwave_link.py's WAVEFORM_MODES table (added 2026-08-25) bundles
          modulation + symbol_rate + fec_preset per mode - the PHY-plugin
          contract - but is currently a documentation/lookup table only,
          not wired into modulate.py/demodulate.py's -t flag or
          fec_encode.py/fec_decode.py's --preset flag, which remain
          independent CLI choices. Follow-up: either wire Waveform Mode ID
          into those flags' defaults (with an explicit override still
          allowed), or decide to keep them permanently independent.

          didn't survive noise.

Phase 8: Over-the-Air Network Simulation - IN PROGRESS
-----------------------------------------------------------
Live, two-process (or more) testing: two ota_station.py stations exchange
real OpenWave frames through the actual modem chain (modulate/pulse-shape
on TX, matched-filter/demodulate/sync/FEC on RX), relayed over the network
through a simulated RF channel (path loss, fading, AWGN, latency) instead
of a one-shot file-based pipeline. Started 2026-08-25.

  [x] 8.1 ota_sim - a new, separate sibling project (/data/Projects/ota_sim,
          own pyproject.toml, zero OpenWave imports) providing the reusable
          channel physics (OTALink: Friis free-space path loss, flat
          Rayleigh fading, AWGN sized to the resulting SNR, configurable
          drop probability, propagation delay + latency + jitter - see its
          README for the full model) and a network relay service
          (ota_sim.simulator, asyncio UDP) that two arbitrary peers talk
          through, anywhere reachable over the network. Deliberately
          protocol-agnostic (only relays tagged IQ-sample datagrams, never
          parses OpenWave frames) so it's reusable by other projects.
          Peers' real addresses are learned dynamically from a "hello"
          datagram (see ota_station.py's register()), not statically
          configured - works whether stations are on the same machine or
          split across up to three.
  [x] 8.2 ota_station.py - the OpenWave-specific live station: builds/
          FEC-encodes/modulates/pulse-shapes real frames on send, and
          matched-filters/demodulates/(FEC-decodes or correlator-syncs)/
          dispatches into LinkReceiver on receive. Interactive (stdin ->
          send, LinkReceiver's on_message -> stdout). --mode selects a
          Waveform Mode ID (see WAVEFORM_MODES); --fec/--ack are opt-in.
          Verified end to end both as an in-process asyncio integration
          test (tests/test_ota_station.py) and as three genuinely separate
          OS processes talking over real loopback UDP sockets.
  [x] 8.3 ACK/retry closed over a live link (see 2.11) - --ack wires
          RetryManager's poll-driven retry loop to real transmit/receive,
          the first venue where this closes over something other than
          phy_sim_loopback.grc's single-process loopback.
  [x] 8.4 In-band mode negotiation - see 8.16. --auto probes the link at a
          fixed control mode, estimates its SNR, and each side grants the
          other the best mode/FEC it measures - no more hand-matching
          --mode/--fec across both stations.
  [x] 8.5 Per-fragment ACK/retry (stop-and-wait) for fragmented sends -
          see 8.16. Not full windowed/parallel selective-repeat (multiple
          fragments in flight, retry only actual gaps) - that would also
          need FragmentReassembler reworked to tolerate out-of-order
          arrival (today any out-of-sequence fragment aborts the run), a
          materially bigger change. Stop-and-wait fully fixes the
          reliability problem this item was originally about (a lost
          fragment used to cost the WHOLE message, not just itself) at
          the cost of one round trip of latency per fragment instead of
          one round trip per message - a real but acceptable tradeoff for
          interactive messaging at this scale. True selective-repeat
          remains a possible future *latency* optimization only.
  [x] 8.6 UDP single-datagram size ceiling (~65KB) bounds worst-case
          on-air sample counts - discovered to bite much earlier than
          expected: --mode 0 (BPSK) + --fec-preset r1_4_k7 (the default
          FEC preset as of 8.7) already can't fit more than a handful of
          characters, not just a near-MAX_PAYLOAD_LEN fragment. Handled
          for now with an explicit pre-flight size check in
          ota_station.py's _transmit_frame() that logs a clear [tx error]
          and refuses to send, instead of asyncio's transport silently
          swallowing the OSError and killing itself (which is what
          happens if sendto() is just called on an oversized payload -
          found by hitting it directly). Lifting the ceiling itself (a
          chunked-datagram scheme, or switching to TCP) is still open, and
          would be needed for bulk transfer over the OTA simulator
          (file_xfer_test.sh already covers bulk transfer over the
          file-based pipeline).
  [x] 8.7 --fec-preset added as an independent override of the mode's own
          WAVEFORM_MODES-documented preset, default r1_4_k7 - and
          ota_station.py -h now prints the actual WAVEFORM_MODES table and
          full PRESETS list so both are discoverable without reading
